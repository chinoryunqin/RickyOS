## 第一关：灰阶沉淀候选（2026-10-09）

- 基线：私有开发仓库 `rickyos-1.2` 的 `b44e910f`。
- 本地开发分支：`codex/rickyos-1.2-design`。
- 没有合并 `codex/rickyos-native-gray` 或 `rickyos-1.2-visual`。
- `ActivityManager` 从规范 Token 取 1500 ms 静止延迟和每 8 次沉淀的 GC16 清理间隔。
- 只有 `wantsGraySettle()` 为 true、没有其他 idle 任务的页面参与。
- 交互帧仍由原页面的 B/W 渲染提交；不是把每次操作都改为 GL16。
- Read Pico 模拟器现在也走沉淀路径，以便验证交互帧/静止帧生命周期。
- 实际运行发现 pinned 模拟器的 `ulTaskNotifyTake()` 忽略超时、无限等待，导致
  idle 沉淀不执行。`patch_rickyos_simulator.py` 对生成的依赖做精确、幂等的适配，
  遵守 [FreeRTOS 的超时和计数语义](https://www.freertos.org/Documentation/02-Kernel/04-API-references/05-Direct-to-task-notifications/03-ulTaskNotifyTake)。
  只用于 `simulator_rickyos`，未改依赖 pin，也不进入设备固件；上游内容不匹配时构建报错。
- 不新增字库、全屏缓冲或 heap 缓存；复用现有 `beginGrayscale16()` 事务。
- 没有改变阅读排版引擎、书籍缓存格式、游戏、微信读书或其他功能。
- 五个主页面尚未按效果图重排，字体、图标和默认封面也尚未落地。

## 第三批：直接灰阶对比候选（2026-10-09）

用户反馈延迟转灰阶观感怪异，要求先按直接灰阶优化几轮再决定。当前本地默认改为
`refresh::kDirectGrayUi = true`，第二批的 B/W＋1500 ms 灰阶方案仅作对比基线。

- `ActivityManager::renderTaskLoop()` 在前台为完整重绘菜单开启原生 16 级事务，
  捕获其普通 `displayBuffer()` 调用，只提交一次灰阶；不安排沉淀 idle 唤醒。
- 复用现有 `wantsGraySettle()` 声明；有自身 idle 任务的页面不参与，阅读页缓存调度保持原样。
  阅读正文、待机图片、自有灰阶事务和增量页面不被这个菜单策略包裹。
- 不因普通触摸／释放取消唯一前台帧；新重绘或 Activity 切换已排队时放弃旧事务。
  页面主动取消不再被管理器提交第二次。缓冲不可用或提交失败时走原 B/W 可读回退。
- 暂沿用 TextTurn 灰阶波形；每 8 个成功菜单灰阶提交做一次 GC16 清理，失败不推进计数。
  唤醒、退出屏保或关闭控制中心带来的强制清理请求映射为 GC16，成功后才消费，
  失败时保留给 B/W 回退。手动清屏重绘灰阶菜单，不显示其近似 1-bit 代理。
- `-DRICKYOS_UI_DIRECT_GRAY=0` 恢复延迟沉淀方案；不新增用户设置，不迁移 SD 数据。
- 没有新 heap 分配或新帧缓冲。直接灰阶只省去正常菜单的先行 B/W 提交和第二次绘制，
  **不能据此声称真机更快或无残影**；面板波形耗时仍待实测。
