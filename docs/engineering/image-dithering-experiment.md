记录于 2026-10-12。用户同意后续做实机对比；**本条仅记录，不代表已实现、刷机或发布**。

参考：[Chaosgoo《Ditherpunk 抖动算法原理与 JS 实时演示》](https://chaosgoo.com/ditherpunk-the-art-of-dithering/)及其 [ESP32 实战篇](https://chaosgoo.com/ditherpunk-the-art-of-dithering-2-esp32/)。文章主要针对低位深、尤其 1-bit 图像；网页导出的 PNG 不是可直接用于屏幕驱动的帧缓冲。

## 实验边界

- **不**对系统文字、图标、分隔线、卡片和阅读正文整屏套抖动。Read Pico 的 16 级原生灰阶继续作为 UI 和照片展示的首选；保持 `refresh::kDitherInChrome = false`。
- 只比较必须生成 **1-bit / 2-bit** 图片的路径：封面缩略图、壁纸或待机图的快速预览／回退缓存。不得把抖动当作刷新速度或残影问题的修复。
- 现有 `JpegToBmpConverter` 的 Atkinson 是基线；候选为预计算、固定种子的蓝噪声阈值。Bayer 只作为网格伪影对照，不作为默认视觉方案。真 16 灰原图也须同屏对照。
- 先缩放到实际绘制尺寸，再抖动并缓存；不要每次翻页或切换页面重新生成，也不要使用每帧变化的随机噪声。优先逐行处理，避免额外整屏缓冲。

## 验收方法

同一批人像、风景、插画与深色封面，固定尺寸和屏幕亮度，在模拟器和 Read Pico 真机上对比：暗部细节、肤色／边缘、规律网点、残影、缓存生成耗时、页面响应及峰值内存。只有观感确实优于现有 Atkinson、且没有明显等待或内存回退时，才考虑替换某一条低灰阶图片路径；不改变全系统渲染策略。
