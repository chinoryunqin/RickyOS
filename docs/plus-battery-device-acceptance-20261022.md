普通串口打开曾触发一次 `CHIP_USB_UART_RESET`；这段单独分组，不拼接成连续运行。
后续改用无 DTR/RTS ioctl 的被动文件描述符读取，重新打开后取到 125101ms 的连续运行样本，
未在该次打开记录中出现启动日志。拔线/重新接线后的具体行为仍需逐次核对运行时间与复位标记。

## 第三轮结论：显示失败，不能判唤醒通过

用户已按流程完成并接回。去重 RAM 环形回放后，有 7 次睡眠尝试：

| 进入→返回 ms（Arduino/esp_timer 时基） | 睡眠耗时 | 返回 | 解释 |
|---|---:|---|---|
|142071→158071|16000ms|0 / TIMER(4)|计时器唤醒|
|158501→158666|165ms|0 / GPIO(7)|共享中断，未归为电源键|
|163742→218741|54999ms|0 / TIMER(4)|计时器唤醒|
|220211→220258|47ms|0 / GPIO(7)|共享中断，未归为电源键|
|225306→278305|52999ms|0 / TIMER(4)|计时器唤醒|
|279808→279813|5ms|259 / UNDEFINED(0)|睡眠请求拒绝|
|284843→328674|43831ms|0 / GPIO(7)|随后确认为短按，328937ms 退出待机|

7 次均记录 cleanup=1。259 在本地 `esp_sleep.h:154` 是 `ESP_ERR_SLEEP_REJECT`
（与 `ESP_ERR_INVALID_STATE` 同值），不能只按通用错误名误判成软件状态损坏。
具体是哪个共享源导致两次提前唤醒和一次拒绝，当前未捕获，不能归因。
电脑连接阶段有拒绝睡眠记录，拔线后才开始睡眠。未发现该次被动捕获中的启动/崩溃标记，
RAM 回放跨拔插连续，但没有玻璃实际画面证据就不能把软件返回算作端到端成功。

**用户报告静置拔线期间屏幕变空白，按侧键也未恢复；本轮整体验收失败。**
重新连接后的原始显示日志确有 `line buffer underrun occurred!`，
`refresh ... result=0x400` / `refresh failed: 0x400`；0x400 是 `EPD_DRAW_EMPTY_LINE_QUEUE`。
不能仅凭通用错误码断言是 LCD、DMA、RMT 哪一项寄存器丢失。

保存所有记录后仅执行硬件复位，没有刷机。重启 ELF 匹配，面板初始化成功，
主页两次绘制结果为 0，用户确认“已恢复显示”。恢复记录为
`display-recovery-reboot.{log,json}`，整体分析为 `trial-analysis.json`。

离线后续候选接入板级已有 `bus_hold_low()` → `bus_latch_for_sleep()` →
`bus_restore()` 浅睡流程；唤醒、拒绝睡眠和清理错误返回均恢复显示总线后才让页面绘制。
没有改充电参数、扩展器方向或外设电源策略。这个候选尚未安装；
恢复显示的设备仍是已重启的诊断 v3，应保持 USB 连接且暂不再进入待机测试。
复用现有 LCD 释放/重建会释放再分配其 DMA 缓冲、描述符和中断资源，
没有新增长期缓冲，但增加每次睡眠的分配周转，需实机验证多轮后堆稳定与分配失败边界。
现有重建 API 初始化失败会 abort，因此离线顺序测试不能代替内存压力/显示恢复真机验收。

离线显示恢复候选的 3 项回归（普通/诊断后端，ASan/UBSan）和完整 ESP32-S31 编译均通过。

## 第四轮结论：再次白屏，停止物理轻睡眠试验

电脑重新枚举 Espressif 303a:1001 `/dev/cu.usbmodem101`。
**本轮失败，不能声称显示总线重建有效。** 缺少失败时回放，不能断言有几次实际睡眠、
在哪个底层阶段停止，或把第三轮的 0x400 自动当作第四轮的实测错误。
原始日志和判断留在第四轮目录 `trial-analysis.json`。
