# UTF-16 TXT / Markdown 支持移交（2026-10-27）

## 问题与范围

用户样书《我在废土世界扫垃圾》为带 BOM 的 UTF-16 LE，原大小 4,462,366 字节。
此前编码枚举只支持 ASCII/UTF-8/GBK，转换失败最终误报“SD 卡读写出错（E3）”。
样书保留在本机，不提交正文、照片或转换副本。

- Plus 分支：`codex/txt-utf16-20261027`，基线 `4b4967c8a5d6a297762229a766ffe6306447ec2b`。
- Pico 分支：`codex/pico-txt-utf16-20261027`，基线 `5cb9b3801b7c73ef1be83aa621d2f55458be358c`。
- 修改在隔离工作树，避免碰到其他任务的 Plus UI 改动。
- 本次按独立开发分支提交和推送；固件尚未刷入真机验收，也未发布。

## 实现

1. 带 BOM 的 UTF-16 LE / BE 流式解码，支持代理对、跨分块字符、CRLF 和中文标题。
   不猜测无 BOM 的 UTF-16，不支持 UTF-32；UTF-32 BOM 会明确拒绝。
2. 目录先解码 Unicode，再识别换行和章节，避免字符内部 `0A` 字节被当成换行。
   目录和阅读进度保留原文件字节坐标，包含 BOM；BMP 字符宽 2 字节，代理对宽 4 字节。
3. 正文输出 UTF-8，沿用现有 TXT/Markdown 转换、目录跳转、进度映射流程。
   UTF-16 Markdown 的表格、标题、链接和延迟换行也使用原文件坐标。
4. 解码器仅有 6 字节状态（其中 4 字节 carry），不增加整书缓冲。
   目录复用原 8 KiB 工作区，释放后转换沿用两个 8 KiB 缓冲，未新增堆分配。
5. 非法/截断编码通过 `ReadError::InvalidData` 上报阅读 E2；真实读写故障仍为 E3，
   内存分配失败单独上报。确定的编码错误不再重复执行 SD 重试。

## 缓存与兼容

详细格式见 [file-formats.md](file-formats.md)。

| 项目 | 新值 | 迁移 |
|---|---|---|
| Encoding | UTF-16 LE=3 / BE=4 | 旧枚举 0/1/2 不变 |
| TXT / 产品 MD 目录 | 3 / 4 | 16 字节头、196 字节记录不变，按书重建 |
| TXT / 产品 MD 转换标记 | 3 / 6 | 按书重建 HTML/sections |
| 非产品 MD 转换标记 | 3 | 同样重建 |
| `txt-map.bin` | 2 | 16 字节头、12 字节记录不变 |

旧 v1 map 只在编码为 0–2 时兼容读取；不得接受伪造的旧 UTF-16 map。
产品 Markdown 在替换旧转换标记 2/3/4/5 前保存源坐标 checkpoint，原进度不删除。
不需要清空整张 SD 卡或删除用户书籍。失败转换不会发布不完整的新 map。

## 验证

- Plus 实际快照源：77/77 定向测试通过，启用 AddressSanitizer / UndefinedBehaviorSanitizer。
- Pico 实际源：77/77 同样测试通过。
- 包括 LE/BE、最小/最大代理对、非法序列、奇数字节 EOF、1/3/7/8191 字节分块，
  目录跨块、代理对进度往返、旧 map 迁移、真实 TxtCache 冷转换和目录热复用。
- 用户原书完整转换 HTML 与独立生成的 UTF-8 参考文件相同；目录扫描也通过。
- Plus 快照可从固定 application/SDK commit 离线重新恢复并通过所有源码 hash 校验，
  新文件和已有移植均保留在 `upstream-plus.patch` / `port-changes.json`。
- 两台硬件固件编译通过；未进行本次真机阅读验收。
- 全量主机测试入口在原基线缺少 WeReadStoreTest 源文件，因此采用独立的真实 TXT
  流程测试入口；不将这 77 项描述为整个系统的全量回归。

测试可复现命令（路径由执行者提供，样书环境变量可省略）：

```sh
RICKYOS_UTF16_SAMPLE="$SAMPLE_UTF16" RICKYOS_UTF8_REFERENCE="$SAMPLE_UTF8" \
python3 scripts/tests/run_txt_utf16_tests.py \
  --app-root "$APP_ROOT" \
  --gtest-source "$GTEST_SOURCE" --simulator-source "$SIMULATOR_SOURCE" \
  --build-dir "$TEST_BUILD" --cmake "$CMAKE" --ctest "$CTEST"
```

该入口不下载依赖、不访问设备。不同进程的模拟 SD 目录已隔离，避免并行测试相互删文件。
Plus 使用 `APP_ROOT=ports/metalio-e-ink4-plus/firmware/rickyos-plus-1.2/upstream`；
Pico 使用仓库根目录。GoogleTest 和模拟 HAL 依赖来自原测试 CMake 的固定版本。

## 构建与合并提醒

Plus 必须使用补丁 IDF `9a97f6c54ec638111ce55cd36581b3c192f15207`。
体验版本为 Plus `1.2.8-txt1` / Pico `1.2.7-txt1`，不是正式发布编号。
Pico 体验版本号通过忽略的 `platformio.local.ini` 覆盖，不改正式版本配置。

Plus 保持已验收的 q11 显示配置：
`FIELD_DIAG=1, UI_WHITE_MAINTENANCE=1, READER_BLACK_RESTORE_PHASES=4,
READER_RETAINED_BLACK_PULSE=17, READER_QUALITY=1, READER_EARLY_ERASE=1,
READER_FINE_RIPPLE=1, READER_MOTION_PERIOD_US=0, READER_RIPPLE_SPREAD=15,
READER_SWEEP_SPREAD=4, READER_ERASE_OVERLAP_PHASES=0`（均为 `RICKYOS_PLUS_` 前缀）。
这不是将其他显示实验并入正式版本的授权。

合并仅取 TXT/Markdown 解码、错误路由、测试、文档；不要覆盖 Pico 较新的
EPUB/Kindle/封面 API，也不要用根目录的旧 Epub.cpp 整文件替换目标。
Plus 还必须带上记录好的快照补丁和变化清单，不能只提交被忽略的 upstream 目录。

真机验收：将原 UTF-16 书直接放进 `/books`，检查首次打开、中文/生僻字、目录跳章、
返回重开恢复进度；再抽测原 UTF-8/GBK TXT 和 Markdown。确认不再报错误 E3 后再发布。
本地安装包、哈希、构建及测试日志见本次 `output/firmware/txt-utf16-20261027` 目录。
