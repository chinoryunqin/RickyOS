# Plus P14 恢复复位：离线逐位与调用链核查

日期：2026-10-23。仅离线分析；本轮没有访问设备、刷机、重启设备或修改生产固件。充电参数、电量模型及欠压/电源毛刺保护均未修改。

## 当前结论与证据边界

实机已知：static4 的第二次浅睡成功返回，`cause=4 err=0 timers=2`；有效 RTC 记录最后阶段为 27（P14 写入前），下一阶段 28 未提交；随后启动的芯片复位分类为 `ESP_RST_PWR_GLITCH`。

**不能据此断言“P14 上电浪涌已经查实”。** 阶段27先于共享锁、Wire 传输及阶段28的 RTC 提交；最后记录为27还包含阶段28提交被打断的可能。既没有 I2C ACK/返回值的跨复位记录，也没有电源波形。确认的是复位窗口，不是该窗口内的具体电气事件。

本轮新增证据：生产板级函数、生产 TCA9555 写入层和生产 Wire 封装接入电脑端假硬件回放，原厂板级函数也通过同一封装作对照。两边各128轮正常序列均通过 ASan/UBSan。故障注入另复现了“按键方向恢复失败，仍执行P14写入”的检查缺口。此缺口原厂也有，尚无现场证据证明它触发了本次复位。

## 正常 Port1 的实际写入

当前与原厂 `config.h` 位定义一致；P14 是扩展口 Port1 bit4，不能当作 ESP GPIO14，也不能仅凭宏名认定真实板上的负载。

| 位 | 厂商源码名称 | 本序列预期 |
| --- | --- | --- |
| P10/P11 | 音量键 | 睡眠输出空闲高，恢复后输入 |
| P12 | 触摸电源/RST | 保持输出高 |
| P13 | 关机脉冲 | 保持输出低 |
| P14 | 蓝牙/功放供电；其他注释称VOUT | 睡眠低，恢复高；实际网络须由板图确认 |
| P15 | 未分配输入 | 睡眠输出低，恢复输入 |
| P16 | RTC中断输入 | 睡眠输出低，恢复输入 |
| P17 | 电源键 | 睡眠与恢复均输入，低有效 |

| 阶段 | 输出寄存器0x03 | 方向寄存器0x07 | 说明 |
| --- | --- | --- | --- |
| 入睡前校验 | 0x87 | 0x80 | P14已低，P17输入，P10/P11输出高 |
| 按键恢复成功后 | 0x04 | 0xe3 | P12高，P13/P14低；按键恢复输入 |
| P14恢复 | 0x14 | 0xe3 | 仅bit4从0变1 |

实际发送：7位地址`0x20`、寄存器`0x03`、数据`0x14`、STOP。接着才写Port0寄存器`0x02`以恢复P5。生产 `pca9555.c:49–63` 的马达合并只作用于Port0，不会改Port1的P13/P14。

依据：当前 `components/metalio_board/config.h:65–108`、`display/epd_board_metalio_eink4_plus.c:35–64, 214–253, 419–477`、`bus/pca9555.c:49–80`、`bus/plus_i2c_wire.cc:44–50`。以上当前路径均相对 `ports/metalio-e-ink4-plus/firmware/rickyos-plus-1.2/`。

## 所有者与并发边界

- 当前板级文件拥有 `s_p1_out`；写入者包括初始化、睡眠屏蔽/恢复、P14恢复、触摸复位P12、关机脉冲P13。没有在普通静态待机路径发现独立的后台Port1写入者。
- P13高写入只在 `p1_pwr_pulse_set(true)`，由关机脉冲序列调用；当前应用入口是 `PlusBoard.cpp:208–218` 的关机hook。它与同步待机循环不是同一条调用路径。
- P12复位调用位于板级初始化和厂商触摸初始化。SDK的Plus触摸轮询只通过共享锁读取触摸地址，不写Port1；非Plus的`MetalioEink4Board`后端由另一设备宏保护，不能混作Plus写入者。
- `s_p1_out` 的读改写发生在共享I2C锁之外，因此**不能宣称它对任意并发调用都安全**。当前调用关系没有证明存在这种并发；离线正常序列通过也不能排除内存损坏或现场未记录的并发。

据此只能降低“正常P14恢复代码误发P13关机脉冲”这一解释的可能，不能宣布硬件关机网络已被完全排除。

## 已复现的检查缺口

`epd_board_metalio_eink4_plus_ioexp_restore_keys()`（当前板级文件461–477行）忽略四次写入和两次读取的返回值。调用方 `PlusBoard.cpp:390–402` 随后执行P14恢复；扩展口回读校验在P14/P5恢复**之后**，来不及证明P14写入前的真实方向/锁存状态。

故障注入：令方向寄存器0x07写入超时，假硬件仍保持0x80，软件函数照常返回，随后向0x03写0x14；static4的分步恢复也返回成功，因为它只检查自己的两次电轨写入。原厂板级函数在相同注入下同样继续。

所以需要纠正此前“第二次唤醒后按键已恢复”“P14之前I2C已成功”的表述：阶段16之后出现17/27只证明函数执行返回，**没有证明里面的事务成功**。第一轮完整通过并再次入睡，也不能代替第二轮状态证据。

本轮不把这个检查缺口包装成已确定根因，也未据此改写恢复策略。后续离线修复设计必须把写入错误和P14之前的真实寄存器状态作为前置条件；不能只增加延时或在电轨恢复之后补检查。

## I2C、PM与芯片复位分类

当前编译使用本地 Arduino 4.0.0-RC1 的新IDF I2C驱动：`cores/esp32/esp32-hal-i2c-ng.c:116–136` 设`allow_pd=1`；但本地IDF `components/esp_driver_i2c/i2c_private.h:48` 的保留链要求 `SOC_I2C_SUPPORT_SLEEP_RETENTION && CONFIG_PM_ENABLE && CONFIG_PM_POWER_DOWN_PERIPHERAL_IN_LIGHT_SLEEP`。static4配置PM关闭，因此不能把该选项解释成“硬件保留恢复实际已启用”。

同时，原厂 `sdkconfig:2259–2275` 为PM开启、CPU浅睡断电开启、**外设浅睡断电关闭**；当前也没有开启外设浅睡断电。因此“当前没跑I2C保留链，所以丢寄存器”尚不成立，不能直接启用PM/外设断电来碰运气。原厂旧驱动读取采用STOP后再START，当前Wire读取采用组合重复起始；两者是待核实差异，正常P14写事务的寄存器/数据则相同。

当前IDF的 `components/soc/esp32s31/include/soc/clk_tree_defs.h:349` 将I2C默认时钟选为XTAL。因此也不能套用其他芯片的“APB降频导致I2C时序改变”直接下结论；软件默认时钟配置不是第二次唤醒后的实测寄存器状态。

本地IDF `components/esp_system/port/soc/esp32s31/reset_reason.c:21–72` 将芯片原始 `RESET_REASON_CORE_PWR_GLITCH` 单独映射为 `ESP_RST_PWR_GLITCH`，与panic、看门狗、USB复位分开。`components/soc/esp32s31/include/soc/reset_reasons.h:45` 描述其为电源毛刺复位。该分类不能指出是外部供电跌落、外设负载、内部电源/时钟域恢复还是其他触发源，更不能用改保护阈值来消除现象。
