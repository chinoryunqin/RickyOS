# Plus：联网入口、下载进度与静态待机重画

本轮基于 design `73901ae83945d7fdf53d89967dff3750bf8235c0` 和已验证的 LCD 扫描尾部修复，独立保留 Plus 硬件适配。

## 问题与改动

- 字体和待机图片入口复用 `WL_CONNECTED` 的连接。共享 Wi-Fi 选择器在自动连接模式下同样复用，并返回现有 SSID/IP；显式网络管理仍显示网络列表。
- Wi-Fi 子页面消耗进入时继承的 Confirm 按住及其松开帧，避免进入后同一手势立即取消自动连接、打开网络列表。上次网络直接连接失败后允许在新扫描结果中重试一次；仍失败再显示列表，重试有界。
- 字体进度改为有新增 KiB 时最多每两秒请求一次即时刷新，增加“已下载 / 总计 KiB”，低于整套 1% 时也能看到容量推进。最终完成另画确认帧。修改使用既有渲染锁，不引入每块数据的分配或日志。
- 小目录请求沿用 12 秒 socket 上限，同时让 TLS 回退、重定向、断点续传共用一份 12 秒请求预算，预算耗尽作为线路错误尝试下一镜像。阻塞式 DNS/TCP 调用仍可能超过预算后才返回，因此这不是严格的墙钟 12 秒保证；大字体文件保留原有 60 秒分阶段等待与续传。
- 待机下载区分“连接已保存的 Wi-Fi”和“获取图片列表”，记录连接阶段及完整目录阶段耗时。COS 有效响应后立即停止目录线路搜索的既有行为保持不变。
- 静态休眠图片首帧显示后，跳过不影响画面的重画通知；USB/输入方式变更不再触发待机状态栏重画。时钟、日期与无图片的选择界面仍按原流程更新；重新选择图片、切换画面、重新进入待机会清除首帧标记。

`tests/test_plus_static_standby.py` 执行实际待机渲染入口及图片下载入口，检查重复通知不再提交静态图、黑白回退同样抑制、时钟/图片选择界面继续重画、换图后恢复首帧、连接复用及分配失败路径。

完整 Plus 回归套件、9 项国内资源发布/线路测试及 ESP32-S31 构建通过。固件 5,222,560 字节，在 5 MiB OTA 槽内；SHA256 `579d1dcdd169ef84938ee67fc152f45db3aa64ce3436e15380cd4f5576b16c60`。

电脑端只读抽样：国内 COS 图片目录 HTTP 200，2252 字节，约 2.23 秒；字体目录 HTTP 200，3331 字节，约 2.23 秒。这只确认电脑侧当时可达，不能证明设备端加载速度或无线稳定性。

实机仍需验收：再次进入字体下载是否自动连接，下载容量/进度是否推进；待机图片目录耗时；纯图片待机两三分钟是否继续闪屏。无线吞吐和此前校时问题不能据此认定已修复。

## 实机发现与第二版

首版已安装、回读校验，原厂槽保持一致。用户反馈两处列表仍失败；日志 `logs/plus-network-ui-standby-boot.log` 记录连接耗时 6.9 秒，COS 域名解析约 7 秒失败后重复 TLS 1.2 分支的同一解析，四条目录线路合计约 58.5 秒仍无目录。这不是已修复网络的验收。

同一台电脑向设备报告的 DHCP DNS 地址直接查询 COS 域名，返回 5 条回答、rcode=0，耗时约 14 毫秒；设备旧探针对另一域名有一次 44 毫秒回复。这两次查询不是同一时刻、同一域名，不能单独证明 lwIP 的根因。

第二版只在 Plus 上允许真正的致命 TLS 协商错误触发 TLS 1.2 回退，DNS、TCP、分配失败和超时不再重复同一路径。实际生产 `SecureClient::connect` 方法的主机测试验证该策略及取消/重复调用。首次 HTTPS 的既有有界探针增加 COS 域名对 DHCP DNS 的直接 A 查询，与 NTP 域名查询同时运行；回复只用于诊断，不用于覆盖解析结果或建立 TLS 连接。

第二版文件 `RickyOS-1.2.0-plus-design-73901ae8-dns-probe.bin`，5,222,720 字节，SHA256 `428bdeb2b55ee134b1554c46b2809dc75662042a1b08283c4caa2f0c0abb6788`，72 项源适配，另含自有 Plus 探针组件修改。构建与五项联网/待机定向回归通过。设备端 DNS 对照结果及静态待机闪屏仍待验证。

## 同域名对照失败与协议对照版

用户报告 DNS 对照版仍失败。实机日志 `logs/plus-network-dns-boot.log`：DHCP DNS 对 NTP 域名的回复约 8 毫秒，但同一时刻 COS 域名的直接查询无回复，系统解析也失败。不能据此归因于系统 DNS 解析器；后续五项探针全部无回复。三个 ping 请求均无回应，而电脑 ARP 缓存匹配设备 MAC、路由走本地 en0。数据通信故障范围超出 DNS。

构建独立诊断候选，在首次 HTTPS 前进行一次有界协议对照：原模式 `0x47`、B/G/N `0x07`、B/G `0x03`。每种必须连续三轮收到来自 DHCP DNS 的匹配 COS 查询回复，才能保留到本次运行；全部失败则尝试恢复原协议并重连。单次重连等待最多 10 秒；所有 socket 在每轮作用域退出关闭。原有站点配置留在 Wi-Fi 驱动内存，关闭 NVS 持久化的既有策略保持不变，不读取/擦除/写回密码。原子标志防止校时与下载并发启动第二轮测试。

该候选仅用于定位，不是已经验证的正式协议策略。本地临时 `.local/test_plus_network_protocol.py`（不纳入正式回归套件）执行实际重连与对照方法，覆盖原模式成功、N 成功、BG 成功、全部失败恢复、重复模式跳过、超时/计时回绕、不擦除凭据、每次启动仅一轮。没有新增堆缓存；仅固定协议数组、原子标志和现有有界 socket 临时缓冲。

候选 `RickyOS-1.2.0-plus-design-73901ae8-protocol-probe.bin`，5,223,776 字节，SHA256 `94ab04c16647d42953fc9167e9d2645cc38c0827e17da579708275a41f923761`。构建通过，网络策略 host 回归通过；实机对照待采集。

协议对照在 HTTP 目录预算计时之前运行，避免测试重连本身耗尽 COS 请求预算。

补充 host 回归：模拟 30 秒协议对照后，小目录请求仍获得完整 12 秒预算；诊断耗时不挤占实际目录请求计时。

## 顺序 ARP/DNS 诊断准备

协议对照过程中，COS 是第五个并发探针，三个模式下该次 `sendto` 都出现 errno=12；因此该轮不能有效比较 COS 的收包稳定性，不能据此断言三种协议均有无线故障。电脑后续 75 次 ICMP 样本收到 35 次回复；样本在协议恢复后开始，也不能用于比较各模式。

下一诊断版停止自动协议切换，仅在 HTTP 计时前运行一个 COS DNS 请求，关闭其余并发探针，启用 lwIP ARP/DNS 日志。临时编译标记 `RICKYOS_PLUS_NETWORK_AUTORETRY=1` 在正常启动流程完成后自动重试用户正在进行的图片下载，不覆盖 onboarding 或 panic 报告；诊断完成后必须移除此标记和多余的调试日志配置，恢复普通启动。

顺序诊断版同时把自动连接超时从 7 秒延长至 15 秒，与手动连接相同；计时起点从初始化前移到调用 WiFi.begin 前，避免初始化/绘制吞掉关联和 DHCP 的等待预算。实际超时分支 host 回归确认 7 秒不提前失败、15 秒超时后才重试/显示列表。

最终顺序候选 5,228,784 字节，SHA256 `0616648445656530e3ea780b53dc3aea7d77c06a56eb7310ba952f829d2e5bf2`。暂存的协议对照方法仅在 `RICKYOS_PLUS_PROTOCOL_PROBE` 开启时编译，当前候选未开启；只发送一份 COS DNS 查询。

顺序 ARP/DNS 日志中能看到网关 ARP 回复和请求出队，COS DNS 仍无回复；设备接收电脑 ICMP 包后也执行 ethernet_output，但电脑未收到这轮 ping 回复。尚不能认定 DNS 解析或路由器是根因。当前进一步开启 IP/UDP/ICMP 调试，不修改线路或无线协议。

设备只读校验意外发现原厂 2.0.62 与其启动程序已替换旧 2.0.61，来源未确定；分区表未变。更新前保存当前 0..0x580000 前缀及 5 MiB 原厂槽，校验 app/bootloader 镜像 checksum 与 hash 有效，并以固定 SHA256 `da8cbdb873fe2fd11ded0cb5ae82c52d828a730ae717265587a98555327d0aba` 更新预检备份锚点。后续安装仍只写 ota_1 与 OTA 选择元数据；当前 2.0.62 未被本轮重写。
