# Plus 热点／加入网络传书页面排查 · 2026-10-20

## 范围及已复现问题

基于私有 `codex/plus-1.2.3` 的 `98b6405e`，只修改 Plus 固定快照，不合入 Pico 或其他设备的无线参数。
用户反馈：热点传书首页偶尔能打开，文件／字体／设置页常打不开；加入路由器后的网页同样慢。

在用户提供的局域网地址上进行了只读检查，不上传、下载或删除用户文件。实机状态接口报告 `1.2.3`。
顺序访问两轮首页、文件页、设置页、字体页、状态接口，再测试空预连接和四页并发：

- 状态接口普通请求约 28–33 ms，首页约 22–26 ms。
- 文件页两轮均在约 8 s 后超时；设置页同样超时。字体页一轮约 11 s，另一轮超时。
- 一个已连接但不发请求的 socket，让后续状态请求等了约 5,170 ms。
- 四页并发均超时。以上共 15 次请求，9 次失败；是这次受控请求结果，不代表所有用户的失败率。
- 同期串口捕获 `Aborting /settings response body after 10005 ms`；STA 已连接、RSSI -53、`ps=0`，内部堆报告约 18.5 KiB。不能把这些现象直接归因为无线信号或省电。

原始计时、串口和备份保留本地 `.local/`，不提交用户网络地址、设备身份或原始文件。

## 源码证据与本轮修正

1. 本机 IDF 6.1 使用的 Arduino `libraries/WebServer/src/WebServer.cpp:423–480` 是单连接状态机；无请求数据时通过 `HTTP_MAX_DATA_WAIT` 保留连接 5,000 ms（对应 `WebServer.h:66`）。
   Plus 的 `upstream/src/network/CrossPointWebServer.cpp:75` 派生类原本只清理请求参数，没有区分空预连接。增加 750 ms 的**首字节前**空连接上限；有数据或已进入解析／上传的请求不受此新上限影响。仍由原 WebServer 解析并处理请求，不添加服务器线程。
2. 初次候选在派生类构造函数中加入 `NetworkServer::setNoDelay(true)`。后续核对实际 Arduino `libraries/WebServer/src/WebServer.cpp:68–78`，发现两个 `begin()` 本来就会开启该选项。因此这是冗余设置，不能称为新增的 Nagle 优化，也不能把主机桩测试当成真实服务器生命周期的增益证据。当前安装镜像仍保留该无实质增益的调用，尚未为这一清理单独重刷。
3. `upstream/src/activities/network/CrossPointWebServerActivity.cpp:291–293` 原来忽略 DNS 监听返回值。现在失败时释放 DNS 对象、记录错误，保留屏幕 IP 的直连服务，而不是假报引导服务正常或关闭可用网页。
4. `upstream/src/network/CrossPointWebServer.cpp` 的 `handleNotFound()` 原来用相对地址 `/` 跳转。改为当前热点 IP 的绝对 HTTP 地址并禁用跳转缓存；硬件热点首页从探测域名进入时也转到设备 IP。普通 STA 路由、API 404 和 OPTIONS 204 保持原有行为。模拟器没有 `hostHeader()`，相关硬件检查不参与模拟器编译。
5. 静态页面发送完成后记录 `WEBHTTP page/bytes/send_ms`，不记录查询参数、密码或请求正文，便于分辨排队和发送耗时。原有 10 s 发送停滞边界、60 s 响应总边界没有放宽。

第一轮无新增任务、全页缓冲或常驻堆分配。跳转复用已有响应头的短 `String`；连接上限为编译期常量。第一轮没有改变网络发射功率、Wi-Fi 缓冲数量、PSRAM 分配策略。

## 第一轮实机结果及第二轮方向

用户重新进入加入网络后，同样请求检查两次：顺序访问的文件页约 143–233 ms、设置和字体页多为 23–40 ms（其中一次设置页 137 ms），均完整返回；空预连接后的状态接口约 556 ms（测试预先等待 200 ms，故总等待对应 750 ms 上限）。
但四页并发首轮 3 次失败、复测 4 次失败，串口确认 `/files` 正文仍在 10 s 后中止。此时 STA 已连接、`ps=0`；顺序测试后内部空闲堆约 43–47 KiB，并发失败时约 32 KiB。
**第一轮没有解决并发问题，不可按已修复发布。** 刷机重启也会改变内存基线，不把所有前后差异归功于 TCP_NODELAY。

第二轮试验使用 SDK 已支持的网络 PSRAM 优先分配：

- 当前 IDF `components/esp_wifi/esp32s31/esp_adapter.c:67–92` 通过 `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP` 控制 Wi-Fi 通用分配优先 PSRAM；`components/lwip/port/include/lwipopts.h:1742–1749` 同时控制 lwIP 分配。不是推测 S31 支持，也不手工改 DMA 缓冲指针。
- 仅 Plus 的 `firmware/rickyos-plus-1.2/sdkconfig.defaults` 启用该项，配套 SDK 要求的 16 个静态 TX 缓冲和 32 个发送缓存上限。TX 静态池约 25.6 KiB 内部 RAM（按 SDK Kconfig 的每个约 1.6 KiB），用受界限的硬件池换取发送时的可用性；普通网络包及管理结构优先用 PSRAM，失败仍按 SDK 规则回退内部内存。PSRAM/内部净变化和并发稳定性须实测，不保证必然改善。
- 不改变已有 24 个静态 RX、64 个动态 RX、16 个 RX BA 窗口、5 dBm 功率兼容策略、TCP 窗口或驱动波形。没有新线程或应用级整页缓冲。
- 发送超时增加块内进度、错误号、内部空闲/最大块的诊断，原有发送时限没有扩大。
- 构建脚本支持独立 `RICKYOS_SDKCONFIG` 和 `RICKYOS_SDKCONFIG_DEFAULTS`，不手改生成配置。`check_plus_web_memory.py` 校验实际生成头，拦截旧配置缓存忽略新默认值的构建；`test_plus_web_memory.py` 覆盖缺少各配置项时拒绝。

保留当前配置再应用新版默认值的本地试验方法：`RICKYOS_SDKCONFIG` 指向新文件，`RICKYOS_SDKCONFIG_DEFAULTS` 依次列出原 `firmware/rickyos-plus-1.2/sdkconfig` 和新的 `sdkconfig.defaults`，以分号分隔；之后同一构建目录记住该配置。两者使用绝对路径。最终以生成头检查通过为准，不能仅看默认值文件。

## 同镜像客户端复核与当前状态

后续保持第二轮固件不变，没有再次重启、刷机或调整无线参数；各检查先后运行，不叠加不同压力工具：

- curl 四路并发 16 次，16 次成功；Python `http.client` 四路并发 16 次，16 次成功。
- curl 使用 urllib 同样的 User-Agent 和 `Connection: close`，8 次全部成功；不能简单归因于这两个请求头。
- 只注册 HTTP 处理器的 urllib 对照先通过 8 次，随后包含 JSON／gzip 完整性检查的 50 次全部成功，最慢约 757 ms。
- 原 `build_opener(ProxyHandler({}))` 增加建客户端、响应头及正文分段计时后，22 次全部成功；再次按原客户端执行十轮页面并发及两轮 API／JS 检查，50 次全部成功，WebSocket 握手也成功。原失败的 50 次报告完整保留，不用后来的成功覆盖。
- 实际浏览器确认文件页完整显示目录和文件表、字体页从读取状态进入已安装字体列表。继续验证设置页时浏览器控制被 Work 设置禁用，停止 UI 操作，没有绕过该限制；HTTP 检查中设置页有完整响应，但不把它等同于设置页完整浏览器验收。
