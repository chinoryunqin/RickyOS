# Plus 厂商源码同机网络对照（2026-10-15）

用户授权继续在连接电脑的本机做无人值守厂商对照。当前测试源为 CloudZao/Metalio-E-INK4-Plus 的公开 HEAD `b400605e9a6a276a2c39864c0cff63798c78e8d8`；该仓库的 PROJECT_VER 仍写 `2.0.61`，不能据此说这是厂商演示的确切二进制或版本。

## 当前结论

- 在这台设备、同一卡和网络中，厂商板级 + Wi-Fi/HTTP/TLS 源码也复现了超时/慢传输，不能把问题仅归于 RickyOS 下载器或列表内容。此构建仍有诊断入口和 SDK 差异，不能称为厂商演示的原封不动固件。
- 相同 b/g/n 挂载镜像前后两次回测都慢于中间卸载/跳过 SD 的测试，SD 状态相关性可以重复；仍不能据此判定卡坏、射频硬件坏或具体 SDK 缺陷。
- 5 MHz 有改善但未稳定完成；首轮 COS 连接超时在无 SD 时仍存在，至少要分别分析连接建立和持续传输。
- 1 线构建未形成有效联网结果，不纳入速度比较。全部诊断结束后已恢复原 RickyOS，整片 Flash 与测试前备份一致；用户书籍未参与传输测试。启动验收见文末。

## 对照构建

沿用此前可编译厂商包的依赖，生成公开归档缺失的语言头；源目录为 `.local/vendor-official-network-compare`。使用 ESP-IDF `fff9895c82d744c7237be8847347bdd1b07c6643`（版本串 v6.1），Wi-Fi 二进制库 `7cd4d7b2`、PHY 库 `5695f4f3`。RickyOS 当前使用 IDF `9a97f6c5`、Wi-Fi 库 `cce8a732`、PHY 库 `b88e4b76`，这项 SDK 差异保留为待区分变量。

三项 mbedTLS 配置在生成的 sdkconfig.h 中均确认开启。厂商 `components/esp-wifi-connect` 与 `components/esp-ml307` 的全部已追踪文件逐字节与 Git HEAD 校验一致，包括 Wi-Fi Station、HTTP、TCP、SSL 实现。

测试入口替换 Application::Start：实例化厂商完整 Board 进行显示/供电/触控/SD 初始化，再调用厂商 WifiStation 和 Board::GetNetwork()->CreateHttp。使用厂商 PowerNeed::OtaDownload 保持网络活动、关闭无线省电；这是测试资源需求，不启动 OTA。自动读取设备上已有 RickyOS Wi-Fi JSON，校验密码长度/CRC 并在设备内解码，再经厂商 SsidManager 接口导入临时 NVS。未把网络密码导出到主机或打印。

这是厂商板级和网络框架的源码对照，**不是完全未经修改的原厂二进制**。另外跳过最新提交新增的触控芯片固件升级；不运行完整 Application 启动中的 SD 升级扫描、云端升级检查及会话清理。测试数据只计数和校验，不安装字体或写入下载文件。

## 备份与启动兼容性

先保存并校验新的完整 16 MiB Flash：`.local/device-installations/vendor-official-compare-20261015/pretest-flash.bin`，SHA256 `e7f44325934e38c66e87c111c83e4b96e27e2f6d72b6a9a44da55cfb8926e96c`。原应用 ELF 为 f2aa0ef55…，原启动程序 IDF 9a97f6c5；分区与原 OTA 选择一致。

第一次保留新启动程序、只写旧 SDK 厂商应用时，在业务入口之前持续 CPU_LOCKUP_RESET，未形成任何网络结果。停止后临时写入同一次厂商构建的配套启动程序，应用正常启动并进入自动测试。该次配套验证表明不能默认两个 SDK 的启动程序/应用可混用。临时启动程序 22224 字节、SHA256 `23f69389ea72a1c384b122a6c9057e677496f7467b96e269120091676c259427`；原启动程序及全部 Flash 已留存，收尾时一并恢复。

## 厂商默认协议

对照镜像 3958064 字节，SHA256 `6a7042959c94d4d3fc924f2c15a47dbd647ecec6c7f980623796db00bf775d36`，ELF `380f20935…`。启动日志匹配，成功连接同一 AP，RSSI -52，协议位图 0x47，协商 HE20（Wi-Fi 6），内部空闲约 90 KiB。

两轮四项请求全部未读到数据：COS 字体列表、Fastly 列表、COS 字体前 1 MiB 均在约七秒时 getaddrinfo 返回 202；不使用 DNS/TLS 的局域网 HTTP 两轮均约十五秒失败。厂商源码栈在本机和当前网络中同样可复现；尚不能据此区分 AP 互通、设备硬件、共享 SDK/配置因素。

日志 `logs/vendor-official-matched-run.log`。下一组只把协议限制为与 RickyOS 相同的 b/g/n，再做同样两轮请求。


## b/g/n 对照结果

限制协议调用返回 ESP_OK，日志确认位图 0x7、协商 HT20，内部空闲约 91 KiB。第一轮 COS 列表 TCP 选择超时；Fastly 列表约 8.7 秒成功。第二轮 COS 列表约 3.5 秒、Fastly 约 2.2 秒成功。

局域网两轮分别约 45.4 秒读取 394560 字节、45.7 秒读取 260640 字节，约 8.7/5.7 kB/s，均没有完成 1 MiB。COS 字体两轮只读取 81362/328382 字节，未完成预定前 1 MiB：第一轮记录了 HTTP 内容读取超时，第二轮达到了测试读取预算。由此在厂商板级/网络代码中复现了慢传输和超时，现象不限于 RickyOS 下载器。关闭未读完的请求也会触发接收线程的 -0x004C / Connection closed prematurely 日志，不能把这些收尾日志单独算作服务端主动断开。

电脑 en0 直连获取 COS 列表为 3331 字节、CRC32 08d4e11c、约 0.54 秒，JSON 可解析、四个字体家族；设备成功返回的列表长度和 CRC 一致。列表内容错误不能解释当前表现。日志 `logs/vendor-official-bgn-run.log` 和 `logs/vendor-compare-cos-list-control-result.json`。

第一组厂商默认协议启动日志已明确：PHY 库版本 100 发现旧校准数据不可用，自动执行完整射频校准。RickyOS 的 release/v6.1 PHY 版本为 101。完整校准之后，两轮默认协议及后续 b/g/n 仍失败/缓慢；因此不额外重复手动擦除校准来替代排查，最终会恢复原 NVS（包括原版本校准数据）。

下一组在载入网络信息后停用已初始化的 Wi-Fi、卸载 SD，再重新初始化 Wi-Fi，用相同 b/g/n、相同请求排除 SD 外设影响。卡内书籍不参与测试。


## 卸载 SD 对照

保持 b/g/n 和其他网络代码相同，载入网络信息后卸载 SD（必要时先停用已启动的 Wi-Fi），再初始化 Wi-Fi。日志确认请求期间 SD 未挂载。与前一组一样只出现一次 Wi-Fi 初始化，未观察到额外无线重启带来的混杂。

两轮 LAN 的 1 MiB 均完成，分别约 38.1/38.0 秒，CRC32 均为 153b9c32，与电脑生成的 1 MiB x 测试数据一致；两轮 COS 的前 1 MiB 均完成，分别约 39.8/40.5 秒，CRC32 均为 cff0abca。比 SD 挂载组更完整、更快，但首轮 COS 连接仍超时，列表仍有数秒等待。

**1 MiB 上限是主动截断测试**：COS 文件完整大小 1763452 字节，因此 cap=1 后 Close 导致的 SSL 接收错误/未收完整文件日志属于预期收尾，不计为额外失败。LAN 文件恰好 1 MiB。

当前只能说 SD 状态相关的线索值得继续验证，不能从一次顺序对照确认因果。后续从启动起跳过 SD 初始化，直接使用上一组临时导入的厂商 NVS 网络信息，以排除已挂载后残留的初始化影响。


电脑另对 COS 字体做 Range=0–1048575 读取：206、1048576 字节、约 0.80 秒，CRC32 cff0abca，与设备卸载 SD 后两轮的前 1 MiB 一致。证明成功读取部分的内容完整，速度差异不能用“列表/字体内容坏了”解释。


## 从启动起跳过 SD

仅在诊断构建跳过 Board 构造中的 MetalioSd_Init，使用上一组已临时导入的厂商 NVS 网络列表，避免为了读网络配置而再次初始化 SD。日志确认没有 SD_HOST 初始化，只有一次 Wi-Fi 初始化，RSSI -51、HT20、内部空闲约 91.5 KiB。

两轮 LAN 的前 1 MiB 完成：35.4/33.8 秒，约 29.6/31.1 kB/s；两轮 COS 的前 1 MiB 完成：36.6/34.6 秒，约 28.7/30.3 kB/s；全部对应 CRC 与电脑一致。首轮 COS 仍连接超时 11.3 秒，Fastly 列表约 8.9 秒；第二轮列表约 1.3/1.6 秒成功。卸载与不初始化 SD 的吞吐较接近，均比最初 SD 挂载组明显更好，但距离电脑侧的速度仍有差距。

为排除测试顺序或 AP 临时状态，随后重新刷入**完全相同 SHA256 的原 SD 挂载 b/g/n 镜像** `90b8f77f…` 回测，记录在 `logs/vendor-official-bgn-retest-run.log`。


## SD 挂载原镜像回测

再刷回最初 b/g/n + SD 挂载镜像（应用 SHA256 完全相同）：两轮 LAN 分别只读 256320/485280 字节，约 5.7/10.6 kB/s；两轮 COS 分别只读 410238/197438 字节，约 8.1/3.8 kB/s，均未在预算内达到 1 MiB。首轮两张列表都连接超时，第二轮列表约 4.8/5.4 秒成功。

相同镜像的前后两次挂载测试都慢于中间的卸载/无初始化测试，支持继续排查 SDMMC 与无线共存，而非只根据一次时间顺序作判断。不过这是单台设备及当前 AP 的少量对照，不能单独确认是卡、板级电气或共享 SDK 驱动的问题。

设备报告的卡参数：SDHC、15200 MB、产品名 asdfg、默认卡时钟 20 MHz。这是设备读取到的 CID 产品名，不据此判断卡的真伪或质量。下一组保持 SD 挂载，只经公开 sdmmc_host API 将卡时钟降至 5 MHz，并记录实际生效值。


## SD 挂载、5 MHz 对照

保持 4 线挂载，调用 sdmmc_host_set_card_clk(slot, 5000) 返回 ESP_OK；实测时钟从 20000 kHz 降为 5000 kHz。首轮 LAN/COS 前 1 MiB 均完成，分别 41.292/37.902 秒、25.4/27.7 kB/s。第二轮在读取预算内仅收到 931680/991286 字节、20.7/21.1 kB/s，未达到 1 MiB。首轮 COS 列表连接仍超时 10.519 秒，第二轮列表成功。降频有改善，但未形成稳定修复，不能直接合入正式固件并宣称联网恢复。

用户确认厂商演示设备也插着 SD 卡；因此不能推断所有 Plus 插 SD 都会出现该问题，也不能把结果直接归责于用户的卡。当前关联仅限本台、当前卡及当前网络/构建组合。还需区分总线配置、卡的电气行为、板级差异和 SDK 驱动。

5 MHz 测试后已恢复原启动程序、NVS、应用与 OTA 元数据；整片 16 MiB Flash MD5 与测试前备份一致，无额外改变扇区。恢复启动日志确认 f2aa0ef55… / IDF 9a97f6c5，进入 InxRecent。随后继续准备仅改为 SD 1 线、保留 20 MHz 挂载的对照，以进一步收窄变量；该实验结束后仍恢复原系统。


## 1 线测试的 USB 采集恢复

1 线构建首次采集在 EPD 初始化日志后停止，未记录到 SD 和网络阶段，不能作为联网结果。常规 USB-Serial-JTAG 下载复位未收到数据，OpenOCD 读取 USB 字符串描述符返回 LIBUSB_ERROR_IO。针对唯一且串号已核对的 ESP USB-JTAG 设备执行 libusb_reset_device 返回 0，随后 esptool 立即重新连接成功、MAC 核对一致。此过程不写 Flash；同一诊断应用重启后重新采集。当前只能确认 USB 传输状态异常，尚不能从日志缺口判断 CPU 在 EPD 初始化挂死。


## 1 线对照未形成有效结果及最终恢复

诊断仅把 SdCardManager 的 slot.width 从 4 改为 1，保留默认 20 MHz；网络源码未改。构建成功，镜像 SHA256 959092144f268925b5e6813d4dc071385f4557a777d327fb942f4fd9b7bcfb5f，ELF 27c8786ca…。第二次采集出现重复的 app_init / EPD 初始化标记，仍没有 SD 初始化成功或联网结果；未观察到 SD 阶段，所以不把它归类为“1 线模式网络失败”。停止采集后再次重置 USB 传输，ROM 连接和 MAC 校验成功，立即恢复原镜像。

最终恢复脚本正常退出，原启动程序、NVS、ota_1 应用、分区表与 OTA 选择均恢复；16 MiB Flash MD5 与测试前完全一致，无额外改变扇区。证据：logs/vendor-official-1bit-final-restore.log，私有备份目录 restoration.json。临时 LAN HTTP 服务已停止。

下一步需要的关键对照是厂商演示的确切 SDK 提交 / sdkconfig / 可启动固件，以及本台换一张已知正常 SD 的同条件测试。用户已确认厂商演示机也插卡，不能以“厂商没插 SD”解释差异。单线构建的早期启动异常则应独立分析，不与已完成的六组网络数据混算。当前未把降频或卸载 SD 作为生产修复，网络稳定性仍未通过验收。

官方接口说明：[SDMMC Host Driver（ESP32-S31）](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s31/api-reference/peripherals/sdmmc_host.html) 支持配置总线宽度/频率，并指出时钟/宽度配置 API 与事务并发使用的限制。本实验没有在请求期间并发读写 SD，频率设置在网络请求前完成；这不替代正式固件中所需的存储互斥。

最终恢复启动验收：logs/vendor-official-final-restored-rickyos-boot.log 显示原 ELF f2aa0ef55…、IDF 9a97f6c5、进入 InxRecent；本次采集中没有 panic / assert / CPU_LOCKUP 标记。未留诊断镜像运行，未安装新的生产候选。
